# Discrete-event hidden-service model

The hidden-service model studies the time until an *adaptive* adversary identifies a service by trying to gain control of nodes along a path toward it. A single run represents one service over a configured lifetime, using a time-based path sampler and an adversary with persistent state.

## The game simulation
We can think of the hidden service model simulation as a simulation game in the mix setting. The game is between the hidden service and the adversary (one of the above models). The adversary tries to win by de-anonymize the service using any strategy it can i.e. sybil attack or compromise or a combination of them, whichever finishes first. The services uses the defined path selection strategy with given params. The simulation ends when the service lifetime ends or when the adversary wins.

Considering strategies that fixes paths or nodes on the paths, we can define the adversary winning the game as:
1. at least one of the possible paths that the service samples from is fully malicious. 
2. the adversary walks any of the actively used paths through a combination of sybil and compromise. For example, considering a strategy like this:

```
Sender -> [L1] -> [L2] -> [L3] -> R -> receiver
```

The adversary would try to:

```text
    - Sybil attack on R 
    -> Sybil attack on L3 
    -> observe active L2 candidates
    -> compromise OR sybil L2 
    -> observe active L1 candidates
    -> compromise OR sybil L1 
    -> service identity linked to network address
```

note: for more details on the above adversary attack logic, see [adversaries.md](./adversaries.md)

## discrete events?

A long-lived service may serve many clients over many sessions. Rather than simulate each request, this model assumes that the adversary can observe the paths exposed by the sampler and explore them. We do not model the traffic volume or the delay required to encounter a particular path because we assume that the number of paths (`N`) sampled is infinit since the adversary can start many sessions over time.

The model therefore moves directly between events that can change either the available paths or the adversary's control. This avoids checking every second or generating individual packets throughout the service's lifetime.

## Model inputs and state

`HiddenServiceModel` receives a reference to the static mixnet, a time-based path sampler, an adversary, and a deadline in seconds. The sampler and adversary states belong to this service's run and retain their state between events.

The model state maintains: 
- the current simulated time
- an event queue
- initialization and stopping flags
- the number of completed node compromises at the first win. This is only for stats/logging purposes.

## Simulation events

The model combines events from the sampler and adversary in one queue:

```rust
enum HiddenServiceEvent<E> {
    Sampler(E),
    Adversary(CompromiseEvent),
}
```

- **Sampler events** represent scheduled changes to the available paths. Depending on the sampler, these include:
- the expiry and replacement of a stored path or 
- the expiry and replacement of a node occupying a local-topology slot. 
- **Adversary events** represent completion of a pending node compromise. Each event carries the node identity and its scheduled completion time.

Scheduling an event in the past is not allowed. Each component (sampler & adversary) supplies pending events through `next_events()` and processes its own events through `handle_event()`. The model performs a win check after each event processing.

## Processing events

On the **first call to `fetch_next()`**, the model:

1. Collects the sampler's initial events and places them in the queue.
2. Asks the adversary to check for a win against the current sampler at time zero.
3. Collects any adversary events generated by that check.
4. Returns `(0, adversary_won)`. An immediate win also marks the model as stopped.

On each **subsequent call**, unless the model has stopped, it:

1. Takes the earliest event whose timestamp is at or before the deadline and move time directly to that timestamp.
2. Delivers the event to the event creator (sampler or adversary) through `handle_event()`.
3. Collects newly pending sampler events.
4. Calls the adversary's `wins()` and collects newly pending adversary events.
5. Returns `(time_seconds, adversary_won)`, marking the model as stopped if the adversary wins.
